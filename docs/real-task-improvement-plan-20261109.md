**一、目标与完成标准。** 本轮要解决的核心问题是：现有工程机制较完整，但“面对真实问题自主调查、选择实验并交付有效修复”的证据不足。开发与评测形成闭环，最终交付包括代码改进、真实任务集、独立评分链路和完整结果。

目标分别落在三条可检验的问题上：

1. 真实仓库修复：只提供真实 Issue 与原始仓库，Agent 能否定位问题、提交补丁并通过独立测试？
2. 真实性能诊断：从用户现象和业务契约出发，Agent 能否构造可复现场景，再完成诊断与优化？
3. 实验选择价值：在相同起始证据、模型、工具和预算下，按证据选择实验是否优于固定预诊断？

代码完成标准是能力可执行、边界可验证、失败可追溯。效果完成标准是冻结版本在独立任务上取得完整可审计结果。结果可以支持优化，也可以否定优化；不以预设的成功率或 Token 降幅作为交付条件。

选择流程：

1. 在模型推理前冻结候选池、适用范围、仓库分层规则、固定排序种子和最大环境检查数量；同一问题/修复簇只分到一个集合。
2. 优先按基线语言、平台支持、可复现环境和资源需求筛选。源码权限依据原仓库源码树确定，不按标准补丁定位文件。
3. 当前仅支持修改既有 Python 文件。冻结范围后，如果任务实际需要新增文件或修改其他类型，按能力限制记录，不在看到模型失败后换题；不得借 gold patch 为模型缩小范围。
4. 资格检查属于独立评测端，允许用参考修复验证评分环境，但只向被测 Agent 交付公开问题和基线。最终题的参考修复与隐藏输出由评测端保存，开发侧只看资格摘要、环境错误类别和来源指纹；如需人工或开发 Agent 查看隐藏细节诊断，将该题转为开发题，替换只能在推理前按预冻结规则进行。保留所有入选、排除、资格失败及原因。
5. 候补顺序如需使用，必须在模型运行前确定，并在正式推理前关闭替换窗口。看到模型成绩后不补题、不删题。
6. 尽量按仓库划分额外的迁移观察组；若仓库数不足，只称“同/跨仓库的未调试问题”，不能称全新领域泛化。公开历史问题无法保证模型预训练未见过。

性能轨道从上游真实 Issue、回归报告、基准历史及相关修复提交中寻找候选，优先 Python 数据转换、导出、解析、缓存与批处理等可稳定复现的场景。此处仅定义检索方向，没有承诺任何具体仓库已合格。

每个性能任务须具备：

- 问题原始来源、缺陷/回归提交、完整基线仓库和许可证；不把目标函数抽成改写后的简化题。
- 用户可见的现象、公开业务入口与行为契约。任务文本不额外提示正确算法或由标准补丁推导故障函数；原 Issue 本来包含的位置线索可以保留。
- 可审核的原始样例或输入生成依据，明确数据分布、大小、外部依赖和脱敏方式。
- 可信的正确性标准：业务规范、原回归测试、独立可信实现或经验证的历史行为；基线本身错误时不能仅靠新旧输出一致判断。
- 预先声明优化目标是耗时、内存还是二者，并定义不可退化约束。
- 基线与上游修复在冻结环境中表现可区分，测量噪声可接受。参考修复仅用于任务资格，不成为 Agent 目标补丁。

健康对照取自未人为植入故障的真实版本，表达为“在本任务契约、输入与阈值内没有预设必须修复的问题”，不声称程序绝无优化空间。它的用途是衡量误改与有依据的不修改决策。

验收门槛：开发池至少覆盖两个不同仓库接口；资格与输入来源可复核；最终候选清单与隐藏内容由评测端管理。检查过某题隐藏失败并据此调试的任务移入开发记录，不再作为当前版本的独立最终题。

**七、阶段 3：补齐受控复现与独立性能评分，预计 5–8 个工作日。** 这是本轮主要代码开发工作，按以下小步交付。

第一步，将固定工作负载抽象为可信任务适配器。建议 `WorkloadSpec` 包含 `repo_commit`、公开 API/CLI 入口、允许输入类型和规模、公开示例、环境、资源限额、语义契约引用及版本。`ugc-export-v1` 保留为现有适配器，不重写历史基准。

第二步，提供两级复现能力，并准确命名：

| 能力 | Agent 可以做什么 | 必须验证的边界 |
|---|---|---|
| 结构化工作负载配置 | 选择输入规模、分布、重复率、批大小等可信适配器支持的参数 | 参数边界、数据量/内存预估、执行预算；这一级只称配置复现 |
| 受控复现程序 | 提交独立的 Python 驱动/生成器，调用允许的公开接口，生成输入并复现现象 | 代码只在隔离执行环境运行；不修改目标源码/原测试/评分文件；生成器不提供可信评分权 |

拟新增工具契约：`propose_reproducer` 返回版本化 `reproducer_ref`；`run_reproducer` 返回真实观察与资源回执；`run_probe` 绑定 `reproducer_ref + snapshot_ref + probe`。如目标是 CLI，使用适配器声明的可执行入口与结构化参数，不开放任意宿主 shell。

模型生成器、目标仓库与候选都不能在宿主直接导入。执行环境不继承模型密钥、不挂宿主根目录或 Docker 控制接口，默认禁网，限制临时文件、进程、CPU、内存、输出和总时间。AST 检查只作预检，不能作为隔离证明。与真实输入的分布符合性需要独立检查，不能把故意制造的极端输入当成用户问题已经复现。

第三步，明确复现是否成立。Agent 可以提出“在某种规模/分布下观察到问题”的判断，但应用记录的是输入、真实结果和业务条件。无可信契约返回 `needs_requirement`，无法复现返回 `not_reproduced`，证据不充分返回 `insufficient_evidence`；这些都不是修复通过。

第四步，把公开反馈与最终评分拆开：

- 公开探索：源码调查、探针、公开回归和候选试验可以反馈给模型，全部计入探索预算。
- 最终提交：`finalize_candidate` 绑定唯一候选哈希；不修改决策也需要封存结论与证据；随后结束 Agent 回合。
- 隐藏评分：独立进程从原始基线重建候选，使用提前冻结的隐藏输入/分布/种子与测试；结果不再反馈给本次 Agent。不得根据隐藏失败追加第二个候选。
- 数据隔离：评测器单独保存期望输出、评分规则、隐藏生成器和后续输入清单；候选执行进程只接收本次需处理的输入及必要执行包装，评分在外部完成。只读挂载并不等于不可读取，不能把完整隐藏评分目录只读挂给候选。
- 完整性：输出解析、格式/长度限制、比较及判定由可信端完成；候选自报的 `passed`、耗时或内存数字不能直接成为评分。

候选必然能看到正在处理的输入，因此隔离不能证明完全防止硬编码。通过独立输入分布、边界覆盖、补丁审查及异常行为记录降低风险；对发现的特判如实报告，不静默改分。

第五步，补齐多目标验收。所有任务先满足行为契约与原回归；阈值根据开发期的业务要求和测量噪声预先冻结，不统一套用地图夹具的 15% 加速要求。

| 任务目标 | 主收益要求 | 共同约束 |
|---|---|---|
| 耗时改善 | 隐藏代表工作负载上达到预声明耗时目标 | 正确性、轻负载回退、内存上限 |
| 内存改善 | 达到预声明内存峰值目标 | 正确性、耗时回退、测量口径一致 |
| 双目标 | 两项各自达标 | 所有行为与资源约束同时满足 |
| 健康对照 | 根据完整证据正确保持不改，或另行证明提交修改确有收益 | 不改不能自动算成功；错误修改、遗漏调查与证据不足分别记录 |

继续把 profiler 用于诊断，把无 profiler 的计时用于性能判定。开发期校准预热、每次执行时长与重复数；最终阶段固定独立进程重复、配对顺序、漂移检查与噪声门槛，保留全部原始样本。采用进程级采样而非把一次进程内循环当成大量独立样本。可参考 [pyperf 的进程、预热与测量说明](https://pyperf.readthedocs.io/en/latest/run_benchmark.html)，是否引入该依赖由实际适配需求决定。

内存指标按任务声明：现有 tracemalloc 只代表 Python 可追踪分配；涉及原生分配时另加受控进程 RSS 测量，不能换个字段名就宣称覆盖。环境噪声超限记为不可判定；预先允许的复测须同时对两组执行并保留第一次结果，不能择优取值。

拟涉及 `diagnosis.py`、`diagnostic_agent.py`、`diagnostics.py`、`probe_worker.py`、`performance.py`；新增 `workload_spec.py`、`reproduction.py`、`performance_evaluator.py`。MCP 同步传递版本化复现引用与工作负载身份，本地与 MCP 执行同一实验须具有一致语义。参考答案与隐藏报告不进入 Agent 的 MCP 证据目录。

验收门槛：两个真实仓库接口完成基线复现；已知正确与错误候选能被区分；复现程序无法修改测试/评分端；最终提交后无法继续取隐藏反馈；耗时题、内存题、健康题、契约缺失和高噪声都有正确终态。新增能力先用脚本与已知候选验证机制，之后再用真实模型验证自主性。

**八、阶段 4：开发集真实模型试跑与定向优化，预计 3–5 个工作日，API 资源到位后开始。** 先小规模发现真实失败，再修改代码；不直接把全部预算投入最终集。

首批顺序：一个 SWE 开发任务的 R0/R1 配对 → 一个真实性能开发任务的 F0/A1 配对 → 审计调用、预算和评分 → 按实际失败扩大到开发集。严重预算/隔离/评分问题立即停批。不同版本的运行单独归档，不拼接最好结果。

性能线设置三个互不冒充的实验：

| 实验 | 输入与对照 | 能回答什么 |
|---|---|---|
| 复现能力实验 | 现象、公开 API/样例和业务契约；模型自行生成或配置复现；可信端独立检查 | 是否具备从反馈构造复现的能力 |
| 实验选择主对照 | 两组从完全相同的公开复现场景开始，避免把输入差异归因为调度收益 | 固定预诊断和按需选择的成本/结果差异 |
| 完整端到端实验 | 两组均从现象开始，复现、调查、修改、最终评分全部计入 | 整体系统表现；不能把差异全部归因于实验选择 |

主对照的两组定义：

- F0 固定预诊断：由应用按冻结次序执行 CPU → 内存 → 基准，再由同类 Agent 使用证据继续调查和修改。预跑时间、探针与工具次数全部收费。
- A1 按需诊断：同类 Agent 从相同起始复现场景选择探针顺序与数量，可以先读源码、只运行必要实验或有依据地停止。

这是“固定预诊断 vs 按需诊断”，不是“全程脚本 vs 智能 Agent”；固定组后续仍有模型决策。若要声称相较普通 ReAct 的增益，需要另外定义并执行 RAct 组，不能给现有结果换标签。

两组共用模型、完整业务工具能力、上下文上限、源码权限、编辑接口、起始证据、最终评分和总预算。报告初始证据呈现方式差异，因为预诊断结果本来就是干预的一部分。Skills、Investigator、并发读取先关闭；MCP 使用方式保持一致；Redis不作为实验变量。不要同时叠加多个新机制，再将全部收益归因于“自主选择”。

每次选择只记录简短的可审核决策摘要：当前假设、支持/反对证据、下一实验想区分的结果、成本和停止条件。证据引用存在不等于因果判断正确；不把模型自报置信度或“信息增益”当成经过校准的指标。

开发失败按以下路径处理：

| 失败类别 | 首先检查 | 允许的改进 |
|---|---|---|
| 环境/依赖 | 正负例资格、插件、网络、资源与架构 | 修复环境并重新资格，不改测试答案 |
| 无法复现 | 输入来源、API调用、数据规模与契约 | 改进适配器/复现工具，必要时要求补充需求 |
| 定位失败 | 首次证据、搜索结果、实际可见上下文 | 调整检索和证据组织，不按最终答案指定文件 |
| 实验无效 | 是否改变了有效条件、是否产生新证据 | 调整工具反馈、重复保护和实验参数协议 |
| 编辑失败 | 原文/版本/唯一匹配、工具使用 | 简化交互或修复实现，保持权限与一致性检查 |
| 公开通过但隐藏失败 | 业务边界、过拟合、遗漏回归 | 仅开发题用于改进；最终题反馈留给下一版本 |
| 预算耗尽 | 重复探索、上下文体积、恢复调用 | 缩短无价值循环、改善停止；不临时扩组内预算 |

每次代码修复先用对应回归验证，再在开发题做必要复测。无法确认因果时写“待验证解释”，不能把观察到的相关性写成机制有效。

验收门槛：完整真实模型轨迹可回放审计；开发问题有明确处置；两组干预可核对；至少完成一组真实修复和一组真实性能配对，允许结果为失败。验证集仅用于预先安排的候选选择；一旦据其反馈修改版本，就记录其已参与选择，最终集继续隔离。

**九、阶段 5：冻结最终批次、执行并交付，预计 3–5 个工作日，取决于镜像准备与执行时长。**

进入条件：阶段 0–4 的机制门槛已通过；选定策略、最终任务 ID、资格结果、镜像、评分、预算、运行次序及源码全部冻结。目标数量未达成时，先调整计划范围与资源说明，再运行；不得结果出来后更换分母。

第一轮最终评测每题每组运行一次，优先增加独立任务覆盖。模型随机性重复作为另一个预先安排的稳定性实验，不把重复次数当独立任务。组别次序按任务配对随机/交替，性能测量串行，避免与其他基准、镜像构建或重负载工作争用资源。

最终阶段不根据隐藏反馈修改提示词、代码、工作负载或评分；发现实现级阻断，暂停批次、保留现有记录，修复后生成新版本计划。已经查看隐藏反馈并据此调整的题退出该版本的独立最终证据范围。不得只重跑失败项并保留旧成功项。

交付物包括：固定任务清单与筛选记录、环境构建/资格证据、两组配置、真实请求用量、模型可见消息、工具轨迹、复现程序与输入、补丁、原/隐藏验收结果、配对分析、失败分类、未运行列表，以及一条可重复执行的演示任务。

最终报告区分“工程验收完成”“真实批次完成”“某项干预得到支持”。若没有可靠提升，保留基线作为默认，候选作为实验配置；不能为交付而挑选有利任务或强行晋升。

**十、预先定义指标与分母。** 两条轨道分别计数，先公布样本流转再报告比率。

| 指标 | 定义与限制 |
|---|---|
| 任务流转 | 原始候选数 → 按规则筛选数 → 环境合格数 → 冻结正式数 → 启动/完成/未运行数；每次排除有原因 |
| 功能修复 | 官方 resolved / 冻结且资格有效的任务数；无补丁、超时、预算停止不从分母删除 |
| 性能联合通过 | 同一故障任务同时满足正确性、主性能目标及回退约束；分母为冻结的有效故障任务，健康对照单列 |
| 复现成功 | 独立确认复现现象且符合公开业务条件的任务数 / 该实验冻结任务数；极端无关输入不算成功 |
| 健康对照 | 正确不改、确有收益的修改、无益修改、回归修改、证据不足分别统计；不改率不能独立代表质量 |
| Token | 供应商实际输入/输出及缓存用量按原始字段保存；含主流程、复现生成、摘要、恢复及后续启用的子Agent；缺失不是0 |
| 工具成本 | 提议数、拒绝数、执行数、物理派发、缓存命中、探针耗时分别列出 |
| 确定性拒绝率 | 参数/权限/版本等执行前拒绝数 / 工具提议数；不能放进“已执行调用”分母 |
| 冗余执行率 | 同快照/输入/工具/参数、相关证据仍可见且无新信息的重复执行 / 实际执行数；缓存回查单列 |
| 性能收益 | 目标程序的耗时/内存变化，与 Agent 端到端耗时分开；保留输入、环境和噪声 |
| 成本与成功 | 两组全任务总成本、共同通过任务成本、全部成本/成功数同时报告；成功数0时单位成功成本为不可计算 |

“无效探索”不能只按最终失败倒推，也不能把有效阴性实验、必要重读或合理复测计为无效。若另建综合标签，必须统一事件单位、规则冻结，并对无法自动判定的事件双人/双审复核，记录分歧；未完成归因前只报告上述客观分项。

资格失败不算模型能力失败，但必须保留原筛选分母。冻结后出现基础设施错误、清理失败或高噪声，列为不可判定，不偷偷剔除。报告全冻结集上的“确认成功比例”和执行覆盖率；批次未完成时不把运行子集的比率冒充完整成绩。模型失败与环境不可判定分别列数，必要时同时给出不确定项全失败/全成功的范围。

两组按任务配对报告成功/失败四格、通过率百分点差及成本差。区间估计以独立问题为重采样单位，重复运行先按问题聚合，并检查仓库分层结果；30道题或12道性能问题仍不足以证明普遍可靠。小样本没有显著差异不等于两种方案等效。

优化晋升需要同时满足：工程边界没有回退，效果/成本证据与预设目标一致，并说明不确定性。通过率降低而 Token 减少不能直接称降本成功。某项对照置信区间很宽时保持实验状态，不作确定性提升承诺。

**十一、资源与调用预算建议。** 以下为待开发期校准、待批次确认的上限，不是费用预测或本轮授权。历史 30 万 Token 批次已经结束，不能继续沿用其余额。

| 限制项 | SWE 修复单次运行建议 | 性能诊断单次运行建议 |
|---|---:|---:|
| 输入＋输出 Token 硬上限 | 120,000 | 160,000 |
| 模型请求上限 | 24 | 32 |
| 工具提议/调用总上限 | 120 | 120 |
| 候选尝试 | 3次预检尝试；首个有效最终提交停止 | 3次公开候选试验；1个最终候选 |
| 复现/探索执行 | 由公开工具权限限定 | 最多12次物理执行，复现、公开候选测量、探针共用 |
| Agent 总时限 | 900秒 | 1800秒 |
| 最终评测独立时限 | 单任务另设1200秒，按资格耗时校准 | 单任务另设1200秒，按冻结测量矩阵校准 |
| 模型并发 | 1 | 1 |

时间、请求、Token 任一上限先到即停；这些上限不能保证一定跑完。最终评测使用独立、预留的执行资源，不追加模型推理。最终容器数由“输入组×角色×进程重复×测量类型”在计划中展开；第一阶段建议每候选最多24个测量进程、单进程60秒硬限，总时限仍优先。超过该规模必须在冻结前调整，而不是运行时偷偷追加。

建议分批释放资源：

- 首个 SWE 开发配对：2次运行，最多24万 Token。
- 首个性能开发配对：2次运行，最多32万 Token。
- 通过审计后，每种任务再增加一个配对；四个配对累计最多112万 Token。
- 规划中的 SWE 最终30题×2组×12万，上限720万 Token；性能最终18题×2组×16万，上限576万 Token；两条最终主对照合计上限1296万 Token。

以上最终上限不含其余开发/验证任务、额外端到端复现实验、稳定性重复及后续 Skills/委派消融。每个扩展单列预算，不把它们藏在“全量评测”中。若资源有限，先交付开发配对与机制结果，再决定最终规模；小样本不因节省额度而升级为可靠效果结论。

费用按实际模型输入/输出/缓存计费规则另算：各类实际用量×当批单价后求和。本文不使用旧价格估算人民币，也不假设免费额度仍然足够。真实调用前核对模型ID、区域、是否滚动别名、服务端额度策略、批次总上限和源码/计划指纹；优先沿用用户指定的 Qwen-Max，若只能使用滚动别名则如实记录响应模型标识与时间，不称固定模型快照。

镜像准备先生成清单：压缩下载量、展开占用、可复用层及可用磁盘。建议首轮最多2个新增任务镜像、压缩下载不超过5 GiB、新增占用不超过20 GiB且保留至少20 GiB空闲；本机容量不满足则缩小准备批次。正式规模的镜像资源根据真实 manifest 再安排，不能简单把现有一题镜像大小乘所有题。

**十二、停止条件与范围控制。** 普通离线实现、现有镜像测试和文档按阶段推进；真实模型、新下载或外部机器使用先提供具体可审核批次，不在本计划书阶段发起付费调用。

以下情况必须中止相关运行或整批：模型用量未知、费用/额度状态不明、配置或代码漂移、隐藏数据暴露、评分规则不一致、清理无法确认、批次预算到限、持续服务故障或用户取消。停止后保存最后一条可靠记录及未运行名单，禁止静默重试或复用旧输出目录。

以下情况停止某条效果结论但可继续独立开发：任务无法资格核验、正确性契约缺失、噪声无法控制、最终任务数不足或候选优化在验证集明显退化。不能通过删除失败测试、放宽权限、调整阈值或更换成容易题来获得通过。

本轮优先级依次为：可靠评分与预算 → 真实任务接入 → 复现及隐藏验收 → 小批真实失败分析 → 最终独立比较。远程 MCP/OAuth、分布式缓存、更多 Worker、游戏引擎、自动技能晋升及新前端不进入本轮关键路径。MCP、Skills 和 Investigator 保留已有能力，等单项实验选择效果明确后再安排各自消融。

**十三、预期周期与阶段交付。** 预计约18–30个有效工作日，具体取决于环境资格、真实任务供应、模型额度和审计结果。阶段顺序按0→5推进；资料准备可以并行，门槛不能跳过。

| 阶段 | 主要交付 | 可以声称完成什么 |
|---|---|---|
| 0 | 冻结协议、统一预算、暴露记录、审计字段 | 具备可控且可复核的批次基础 |
| 1 | 真实SWE环境资格、Issue-only策略、官方评分接线 | 真实仓库评测可执行；模型效果待测 |
| 2 | 真实任务来源、分组、资格与筛选清单 | 评测对象可追溯；规模以实有清单为准 |
| 3 | 复现工具、多项目适配、隐藏评分与多目标验收 | 产品支持受控真实问题诊断闭环 |
