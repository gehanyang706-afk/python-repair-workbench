# 后端性能基线与任务列表 N+1 修复

2026-10-21。本轮完成离线性能测量、一个已复现的数据库查询修复和完整回归。没有新增依赖、镜像、Redis、模型调用、算法或远端推送。包版本仍为 1.1.0.dev0；Agent 默认 v2，SQLite/MySQL 入口选择不变。

## 最重要的结果

1. 在真实 MySQL、独立 Worker、真实 Docker、真实 HTTP 上完成 1/2/4/4/2/1 六格，每格8个重复夹具任务，共48个任务、144次合成模型调用。全部一代完成、一个候选、原测试范围通过，无HTTP错误、无清理失败。
2. 列表在100条历史时执行101次业务 SELECT 和101个连接/事务。改为一次批量 SELECT 后，公开返回内容 Hash 完全相同，仍剔除幂等键和内容摘要。
3. 同数据只读对照，各接口各30次：列表 HTTP P95 从1341.18ms到40.49ms；详情从14.64ms到15.11ms。没有增加缓存或改变权限、租约、预算、验证和修复算法。
4. 完整离线及MySQL/Docker回归：175项通过，0跳过，133.574秒。包含原168项、新4项测量契约和3项列表查询/数据形状测试。

上述48个任务是同一个已知折扣夹具的重复负载，不是48个不同真实Bug，也不是48次真实模型修复成功。模型每次固定延迟0.25秒并输出测试已知修改。合成token字段仅作回执，不是供应商消耗。模型网络、SDK请求子进程和真实推理成本不在这组性能结论中。

**重要偏差：** 随着任务加入，历史列表规模从77、85、93增至100条，后面三格保持100。伴随查询包括历史列表，所以各格HTTP负载并非严格相同；本机还有其他应用/容器。完整保留六格，不重跑挑选更好结果，不把上述差异归因为纯粹Worker扩展能力，也不据此宣称4 Worker固定提升多少倍。

伴随HTTP探测只有一个持久连接客户端，detail/events/list顺序轮转，每次响应后延迟0.2秒；events使用follow=false。这不是开环压测、接口峰值QPS、海量SSE长连接或断线风暴测试。每个接口的样本数、响应字节和逐次延迟在本地原始数据保留。

## N+1 的复现、修复与隔离对照

旧路径：

```text
GET /api/tasks
  → SELECT id ... LIMIT 100，事务结束
  → 每个ID调用get，重新连接、SELECT、结束事务
  → 拼成列表
```

代码根因是 MySQLStore.list() 把批量读取拆成逐条get。无数据库测试中3条历史产生4个事务，明确失败；真实100条数据进一步测到101次业务查询和连接边界。统计不包含驱动内部的连接握手/会话设置等额外网络消息，不能叫“总共只有101个网络包”。

新路径：一次 SELECT * ... ORDER BY created_at DESC LIMIT 100，在同一事务内读取；离开事务后做相同JSON解码和字段脱敏。排序、100条上限、状态与返回形状不变，幂等键和请求摘要仍不公开。不新增缓存失效问题，也不改任务状态写入。

矩阵结束后确认所有任务终态，再执行前后只读测量；中间没有任务写入。完整响应 Hash 为：

`38ed9f1cc793b7a1abfd4ca54421738b0368d05bf2594a153f3f7083f2f6ebd9`

| 接口 | 样本/阶段 | 修复前平均 / P95（ms） | 修复后平均 / P95（ms） | 业务SELECT/连接数 |
| --- | ---: | --- | --- | --- |
| list | 30 | 1269.70 / 1341.18 | 37.53 / 40.49 | 101 → 1 |
| detail | 30 | 14.24 / 14.64 | 14.25 / 15.11 | 1 → 1 |

任务行数、详情任务ID和完整公开响应Hash前后一致；代码指纹确认只改变 mysql_store.py。直接SQL路径与真实HTTP路径均测量。详情作为未改变查询的参照基本不变，支持收益与列表N+1修复相符；单机顺序30次测量仍不是跨机器的统计保证。

没有在修复后重跑Worker矩阵，因此不宣称新列表查询使Worker吞吐提升。旧矩阵和新接口对照分别报告。

## 为什么本轮没有加入 Redis

已确认的列表瓶颈是N+1业务读取，批量SQL即可消除。本轮没有测量AST索引缓存命中率、源码重复解析成本或大量SSE唤醒，所以不具备引入Redis的正面证据，也不声称Redis对所有场景都无用。

Worker连接次数和事务总耗时还提示连接建立/会话设置值得后续单独分析；当前观测包含客户端开销，不能当成MySQL服务端CPU或锁等待时间。若继续优化，应先明确连接复用的线程/进程边界，再做同版本对照，而不是同时加入连接池、Redis和调度策略。本轮不自动实现。
