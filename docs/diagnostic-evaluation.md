# 公开开发集诊断评测执行器

本阶段把任务准备、配置冻结、串行执行、逐项审计及成对报告接成一个可复现入口。唯一可执行策略是本地确定性 `diagnostic_probe_policy_v1`，没有供应商配置或真实模型启用参数。它验证根据工具反馈选择探针的链路，最后提出 `insufficient_evidence`，不生成补丁。

这不是正式独立评测：四题仍是公开合成开发案例；重复运行不是新增任务，正常完成不是优化通过。当前也没有健康决策准确率或独立内存改善评分。未来真实模型批次须另冻结精确模型、任务、预算及停止规则，不能把当前计划或已有密钥视为授权。

## 一次完整流程

1. 核对已审查 registry、三个可见文件及内容哈希；只准备当前任务，不复制维护方根因、其他题或参考补丁。
2. 固定源码、策略、Skills、依赖锁、已安装依赖版本、Python/平台、镜像不可变ID、工作负载、阈值、共同预算和随机种子，生成计划哈希。
3. 每个“任务×重复序号”形成一对运行，随机决定两配置顺序，整批串行。两边仅 `strategy` 不同，使用相同任务文本、镜像、探针、编辑接口及预算上限，Skills与调查委派均关闭。
4. 从固定内容构造可重复 Git 提交和通过原测试的基线。每个会话有独立探索缓存；两配置只共享不可变基线。
5. 调用真实 Deep Agents 工具循环、原隔离执行器及可选MCP；每项结束核对源码未漂移，交叉审计事件、证据、报告及清理记录。
6. 保存全部预定行、逐项结果、成对差值和未运行项。取消、清理无法确认、源码漂移、任务/镜像/工作负载不符或审计失败都会停止批次，不自动重跑覆盖。

两配置是 `adaptive` 与 `fixed` 的诊断调度对照，不是简历中的B0/Full，也不能据此归因Skills、多Agent或真实推理能力。fixed 的CPU/内存/基准预跑计入同一会话预算，之后的缓存回查也计工具次数，不算新实验。

## 结果维度

| 维度 | 当前记录 | 解释边界 |
| --- | --- | --- |
| 规模与分母 | 预定、启动、各终态、审计通过、成对完整数量 | 缺失、失败、停止与未运行不删除；重复次数不扩大独立任务数 |
| 业务结果 | 候选状态、停止原因、决策提议分别保存 | 当前只读脚本无候选，优化成功率与健康准确率保持 `null` |
| 调用与诊断 | 主子共用的模型包装调用、工具提议/接纳、实际探针及缓存复用 | 包装调用不是模型API调用；控制流差异不是降本效果 |
| 重复观察 | 可核对工具轮数、只有重复而无新观察的轮数 | 单位是工具轮，不冒充“无效工具调用占比”；空搜索等负证据有价值 |
| Token | usage回执数量、缺失数、完整时的合计 | 缺失保持 `null`，未运行不补零；脚本用量不能当真实账单 |
| 来源与资源 | 基线、镜像、脚本、任务配置、原始日志/采样、容器回收 | 哈希是当前一致性清单，没有外部签名，不能检测全部档案被一致重写 |

完整可比较对要求两边正常结束、审计通过且基线一致。报告只给模型包装、工具与实际探针数量的差值，不生成Token节省率、置信区间或LLM效果声明。

现有性能验收契约要求速度改善并约束内存退化；case-03 的内存缺陷标签不能自动转换成“内存优化成功”。本入口拒绝脚本意外产生的候选或委派，不把原有公开验收器冒充隐藏评分器。

## 无模型API的命令

从包含任务集与审计脚本的受审查源码目录执行。Docker仅使用已存在的本机镜像，不下载；所有计划文件和输出目录必须全新。

```bash
.venv/bin/python -m repair_workbench.diagnostic_evaluation plan --dataset benchmarks/ugc-diagnostics-dev-v1 --image repair-workbench-test:20261014-pinned --output runtime/your-new-diagnostic-plan.json --seed 27 --transport local
.venv/bin/python -m repair_workbench.diagnostic_evaluation run --dataset benchmarks/ugc-diagnostics-dev-v1 --plan runtime/your-new-diagnostic-plan.json --output runtime/your-new-diagnostic-batch
```

用 `--task case-01` 缩小计划，`--repeats` 为1–3，`--transport mcp` 选择本地stdio。共同上限可通过 `--max-model-calls`、`--max-attempts`、`--max-probe-runs`、`--deadline`、`--timeout` 与 `--batch-timeout` 固定。它们不是Token或费用硬上限。

`plan` 只做内容校验和本机镜像检查，不启动探针；`run` 执行固定离线策略。成功退出0，拒绝或批次停止退出2。没有任意 provider、factory、外部模块或任务代码执行参数；主机不导入目标仓库代码。

准备任务前拒绝可能改写 Git 仓库、索引、对象或配置的 `GIT_*` 环境；仅允许无关的分页和终端提示设置。`git -C` 本身不能覆盖 `GIT_DIR` 或 `GIT_WORK_TREE`，因此检查在创建任务目录和任何 Git 操作之前完成。旧项目入口未因本阶段改变。

## 归档与复核

批根目录保存 `plan.json`、`results.json`、`runs.csv`、`report.md` 和容器记录；`tasks/` 保存每题源仓库与原测试基线；`runs/<run_id>/` 保存原会话档案、带计划/运行绑定的来源记录及独立审计输出。不会在失败后补写候选、调整阈值或删除首轮记录。

每次运行前后及批末重查计划与源码。除原审计器外，执行器还核对报告的镜像、基线、工作负载指纹和诊断脚本哈希，重新验证语义指纹及原始样本，要求完整日志及CPU原始profile。进度记录须与会话摘要和事件一致，统计后再保存各文件哈希。

本入口需要受审查源码目录中的任务集与审计脚本；安装包不内置这些开发评测数据。CLI不会下载任务或执行 manifest 指定的脚本。
