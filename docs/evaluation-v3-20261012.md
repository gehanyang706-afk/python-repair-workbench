## 失败机制与上下文观测

六题共 23 次有记录的源码读取、0 次重复读取、12 次无效上下文/操作请求。原题 20 次读取、12 次无效请求；跨项目 3 次读取、0 次无效请求。相比 v2 原题记录的 26 次读取，本轮调用为 38 次而 v2 为 40 次，输入 token 为 337,877 而 v2 为 351,872；但 v3 没有产生通过的候选，且采样不同，读取及 token 降低不能解释为有效效率提升。

最明显的新瓶颈在提交前：`set_repair_plan` 要求 2–16 条需求且必须同时包含 change/preserve，负索引题连续九次未满足最基本的数量约束。空转换与 JSONL 各有一次只提供单类需求的计划拒绝，之后成功登记计划，但最后的 `submit_edits` 是模型输出的无效工具调用，未进入 Session。空名称题在没有成功登记计划的情况下提交局部修改，Session 先因 `text_not_unique` 拒绝；拒绝消耗候选名额，但没有构造候选源码或运行 Docker。两道跨项目题分别暴露输出长度截断，以及计划之后的无效提交调用。三次无效 `submit_edits` 均发生在模型响应解析层，不能归咎于 Docker 或独立评分。

`finish_reason` 共 45 次 `tool_calls`、1 次 `length`；最后一轮无效工具调用分别出现在空转换、JSONL 和非正 `max_count` 题。两题因模型调用上限停止，四题由 Agent 自行结束。当前日志能够定位拒绝阶段和错误类型，但没有保留每次工具参数的安全摘要，因此不能在不查看未脱敏完整消息的情况下判断模型为何反复构造少于两条需求，或无效提交的具体字段。

现行调用链：评测器加载哈希固定任务并在 Docker 中做资格核验 → 创建只含公开测试的基线快照 → `full` Agent 获取初始文件结构、按需读取源码 → 登记需求与保留约束及批准符号 → 提交局部修改及覆盖/风险说明 → Session 检查预算、文件版本、范围、唯一匹配与语法 → Verification 在隔离 Docker 中运行公开测试 → 评测器用模型不可见的独立测试评分。此次实际大多停在计划或提交解析阶段，未走到公开测试之后的候选验证。

下一阶段优先解决计划与提交接口的真实可用性：为结构化工具参数建立安全的形状观测与拒绝分布，复现模型实际输出到接口校验之间的失败，再决定是简化必填结构、拆分提交阶段，还是改善错误反馈。保留必要的范围和约束保护，不针对这六题硬编码；先用确定性回放和自动化测试验证机制，再以另行批准的付费对照/消融区分各机制贡献。当前结果没有依据继续宣称 v3 优化带来成绩提升。
