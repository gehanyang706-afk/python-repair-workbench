# 后端性能基线协议

日期 2026-10-21。只使用现有专用 MySQL、参考测试镜像与离线模型替身；无模型服务调用、无新依赖/镜像、无远端推送。

## 固定负载

- 基于 a9790ea 的产品实现，不更改 Agent 策略、测试判定与数据库配置。
- 先用 2 个夹具任务验证测量器；它们单独记录，不计入正式矩阵。
- 正式顺序 1 / 2 / 4 / 4 / 2 / 1 Worker，每格 8 个任务，共 48 个，最多 576 次合成模型调用额度，预期实际 144 次；真实模型调用 0。
- 同一个已提交折扣夹具、相同源码身份和镜像 ID，固定每次 Fake Model 延迟 0.25 秒，正常路径读取→局部编辑→结束三次调用。
- API/Worker 进程预热完成后提交任务；全部入队后释放 Worker 屏障，避免把进程导入时间算入并发扩展能力。
- MySQL 1GB/2CPU、默认租约 15 秒、每任务 12 调用/3候选/180秒/单次测试30秒不变；每格最多300秒墙钟。不同格不并行。
- 专用 test 数据库不得同时运行其他任务或验收；已有终态历史保留。不能删除历史来美化查询延迟。

## 指标及分母

- 队列等待：数据库 first claim 时间减创建时间，包含批量提交过程中较早任务的等待。
- 吞吐：8 个已验证任务 / 从 Worker 释放至最后一次终态轮询的单调时间；每格报告，不当作生产峰值。
- 执行与端到端：分别从 claim/created 至 updated；nearest-rank P95，报告 n，小样本 P95 接近最大值。
- HTTP：持久连接客户端，detail/events/list 顺序轮转，每次响应后等待0.2秒，记录延迟、状态码、样本数和字节数。它是闭环伴随查询，不是固定到达率压测或接口峰值QPS。
- SQL：在测量器中观察事务/连接数、execute 时间和语句种类，不保存参数、源码或凭据；观察本身有开销，所有格保持同一测量方式。
- 资源：每0.5秒采样 API + Worker RSS，并记录 Worker CPU 时间；不包含 MySQL、Docker 测试容器及整机总占用。保留其他本机应用存在的环境限制。
- 每任务必须一代领取、3个完成模型回执、1个候选、公开范围通过；任一异常、HTTP错误、清理失败或源码指纹变化即停止，不自动重跑替换数据。

## 后续有条件的小修整

矩阵结束后，以终态数据库做只读 list/detail 各30次的直接SQL和真实HTTP探测。固定任务返回内容的Hash和行数。

仅在记录确认瓶颈时修复确定性数据库查询问题，再在数据库不写入的条件下重测同一请求集合。新源码/目录单独保存，不把接口小修后的结果混入旧Worker矩阵，不宣称Worker吞吐已改善。

Redis 的引入取决于此轮证据；本轮不因“第二批”名称而默认安装或实现缓存/消息层。测得的工程指标不代表真实模型修复质量或供应商推理吞吐。

## 执行后发现的限制（不回写原始协议）

六格均完成、未重跑。由持久化 created_at 只读重建的释放时历史列表规模为 77 / 85 / 93 / 100 / 100 / 100 条；矩阵内历史增长导致列表负载不是严格相同。该偏差没有隐藏，也没有通过追加运行替换数据。Worker 结果只作描述性基线，不据此宣称因果扩展倍数。

矩阵后另外冻结了100条终态历史，前后读探测确认完整公开响应 Hash 一致；只有 mysql_store.py 的列表查询变化。其30次请求对照可以用于描述本次列表N+1修复的效果，不反推Worker吞吐或Redis收益。
