**公开候选试验与真实问题复现（2026-11-11）**

真实仓库诊断新增可选公开候选试验。Agent 可以先建立独立候选，在同一公开输入上测量基线与候选，再选择保留、调整或放弃。只有首次最终封存才结束工具循环；隐藏验收继续由独立进程执行。原UGC及SWE默认工具不变，本轮供应商模型请求为0。

显式启用 `enable_candidate_preview=True` 时，原生图增加三个受控工具：

| 工具 | 结果与边界 |
|---|---|
| `preview_ref_edits` | 用已有源码引用和唯一原文生成候选；共用候选次数，记录候选内容、补丁和manifest身份；`preview_ready`仅表示可试验 |
| `run_preview_probe` | 只接受已登记候选引用、公开case和注册CPU/内存/基准工具；基线与所有候选共用物理探针额度 |
| `finalize_preview` | 再校验候选版本及补丁后封存原候选，无需重提交同一编辑，也不消耗第二次候选额度；封存后停止模型与工具 |

基线和候选报告分别绑定输入及快照；分页引用只能回查对应版本。重复探针的缓存命中仍计根工具额度，不增加物理派发数。达到探针上限后可以回查或封存，不重置预算。未知引用、路径猜测或内容漂移不能进入容器或最终评分；清理未知封锁后续动作。

预览不修改原始仓库，也不运行隐藏测试。没有可接受候选时可以放弃未封存的试验并提交证据不足或不改提议；该提议仍非独立验收。真实批次若启用此能力，F0和A1共同冻结开关与三项工具，两个变体仍只以预诊断策略为干预。旧实验的冻结配置不自动采用新能力。

**真实仓库工程控制。** 分别在完整的已见sqlparse和more-itertools历史仓库运行原生Deep Agents图，脚本策略使用预先选定的上游源差异。每题6次脚本响应、6次根工具、1个候选尝试，分别对基线和候选派发同一公开case的物理探针。两题都成功回查候选报告并按同一身份封存；容器清理及输入完整性确认。没有启动最终评分。

| 仓库 | 实际公开探针 | 核对结果 |
|---|---|---|
| sqlparse | 基线与候选CPU各一次 | 回查候选热点，封存内容与上游参考逐字节一致 |
| more-itertools | 基线与候选内存各一次 | 原套件717项正常通过；公开输入两版本输出指纹一致，回查Python分配样本后封存 |

more-itertools此次公开输入的Python可追踪峰值中位数为497,548与207,544字节，候选是已知上游实现；这只是该公开试验观察，不是Agent取得的优化收益，也不改变之前最终工作负载的噪声不可判定。两个仓库均已暴露于开发，不能作独立最终集。

**Django公开问题复现。** 另外从`django__django-13315`的公开Issue构造关联模型与内存SQLite数据库，经已接入的实际SWE复现工具运行。两个满足条件的关联行产生表单选项`["1","1"]`；删去一个关联行后只返回`["1"]`，不满足条件的选项保持排除。程序只挂载原始公开基线、由操作方编写，不读取官方测试补丁或标准修复；2次工具、0供应商请求、0官方评分，原始输入和清理确认。它证明可以在提交前取得真实行为反馈，不能记作Agent自主复现或修复通过。
