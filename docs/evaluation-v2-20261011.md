### 负索引：提交可靠性改善，调用效率仍有限

首个 submit_edits 候选完成负索引归一化和越界检查，公开测试及独立用例全部通过。原来两个整文件候选均产生顶层缩进错误，本轮没有重写无关源码。

补丁除逻辑变化外，增加了注释并改写 IndexError 消息，不是绝对最小补丁；当前验收不检查异常消息兼容性。12 次调用中还出现 3 次框架 read_file；现有日志没有保存其参数和返回，不能断言这些读取一定无用。

### 空值转换：能够纠正编辑位置，但遗漏反向路径

第一次局部提交被 line_mismatch 拒绝，返回实际起始行 210。Agent 再次读取源码，第二次提交通过公开测试。这证明本次出现了有效的编辑错误反馈恢复。

独立用例中 `Bits.from_hex('')` 和 `Bits.from_bytes(b'')` 仍失败：候选修了输出转换，却未处理空输入经过 `from_hex` 形成 `'0x'` 的路径。独立结果为 2 失败、4 通过，最终不计成功。

第 12 次调用提交了公开通过的候选，随后框架准备下一次模型调用时触发上限，所以会话 state=stopped、stop_reason=model_call_limit，但候选公开 status=passed。最终评测以独立验收为准；预算结束不能抹掉已生成的有效验证证据。

独立失败没有反馈给模型继续修复，也没有人工修改补丁。

### 空名称：新日志确认本次停止原因，但不能反推历史

本轮 12 次响应全部为 finish_reason=tool_calls，无 invalid_tool_calls，无 length。第一次读取日志，随后 11 次调用 read_source，未提交候选，最后因 model_call_limit 停止。

因此本次失败的直接原因是读取阶段耗尽调用预算，不支持“输出长度不够”或“工具 JSON 无法解析”的解释。事件未记录读取参数，尚无法确认具体哪些读取重复或没有信息增量。

自动 completion_diagnosis 仍是 no_candidate_cause_unconfirmed，因为该字段只对最后一次响应做有限分类；结合完整事件与 stop_reason，可以明确解释预算停止。原基线缺少结束原因观测，历史纯文字结束的根因仍不能追溯确认。

### JSONL：可执行补丁仍可能扩大修改范围

首个局部候选无语法错误，公开测试通过；但将 `-1.0 < rel_seek < 1.0` 改为两端均包含。任务只要求接纳右端点 1.0，并保留非法范围校验。

独立用例验证 -1.0 应抛出 ValueError，实际没有抛出，因此结果为 holdout_regression（1 失败、9 通过）。旧版候选已有相同语义风险，但被语法错误阻挡；本轮首次由动态独立验收证实，未为了得分修改测试。

## 业务调用链与技术边界

旧链路：固定快照 → Agent 读取源码/日志 → 完整文件提交 → Session 限制预算与范围 → Verification 重建原始测试并运行 Docker → Evaluation 独立验收。

新链路：固定快照 → 读取原文与哈希 → Agent 提交局部修改 → Session 计数 → Edits 检查版本/唯一匹配/起始行/重叠 → 构建完整候选 → 去重与语法预检 → 同一 Verification/Docker 链 → 同一 Evaluation 独立验收。

Session 仍是修改权限和预算边界；Edits 只负责安全构造候选，不判断业务正确性。Verification 只授予原始测试范围内通过。Evaluation 使用模型不可见的独立用例进行最终评分。新模型观测记录每次响应及用量，不自动增加调用。代码没有因本轮失败而临时调整。

## 下一阶段建议

优先处理**需求覆盖和约束保持**，再处理读取效率，两者应分别验证：

1. 提交前依据用户任务和可见源码建立受影响入口与必须保留的约束清单，检查正反向转换及未被要求放宽的边界。不能把本次独立用例答案塞入 Prompt，也不能允许改测试换取通过。
2. 补读取范围、内容指纹及返回状态的受限观测，确认哪些调用没有信息增量，再设计有界的读取/提交阶段控制。当前数据只证明连续读取耗尽预算，不足以直接规定“第 N 次必须提交”。
3. 继续用同一模型与预算做独立对照，保持历史负结果；若要证明组件因果贡献或跨项目效果，需要另行批准消融或新项目评测。本轮不自动扩大范围。

局部提交已经让语义问题更可见，但“补丁能执行”与“业务修复完整”仍是两个不同验收层次。
