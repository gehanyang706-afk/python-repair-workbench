# qwen-max 公开任务实测协议（2026-11-01）

本轮验证失败上下文组织是否减少模型调用、源码往返和 Token 开销，同时保持独立验收结果。项目的自适应实验选择、MCP、Skills、Investigator 需要各自的后续实验，本轮不归因于这些机制。

## 批次与基线

- 用户批准沿用电商平台的北京区 qwen-max 配置，确认免费额度充足且“免费额度用完即停”已开启。本批输入与输出合计上限 300,000 Token，额外付费上限 0 元。连接配置只读，密钥不复制、不记录，不修改电商项目开关或账本。
- 使用用户指定的 `qwen-max` 别名，温度 0、输出上限 4096、重试 0、串行。该别名会滚动升级，不宣称固定快照。原生 SDK 使用北京区 `https://dashscope.aliyuncs.com/api/v1`，与同账号的兼容接口属于同区域服务。
- 基线 on_demand：通过工具按需读取日志与源码。
- 优化 failure_context：调用现有失败聚焦上下文机制，将可见失败位置、片段和受控源码引用预置给模型。
- 两组共用 simple_context profile、系统提示、AST/搜索/读取工具、source_ref 编辑协议和独立验证。唯一干预是初始上下文包。预取也计入上下文读取统计，模型输入包含其内容。
- 2 个 BugsInPy 衍生缺陷 × 2 种方案 × 3 次重复，共 12 次任务运行、6 个配对；按题和重复交替先后顺序。重复次数不充当缺陷数量。
- 每次最多 12 轮模型调用、3 次候选、100,000 Token、240 秒；工具上限沿用 session 的 60 次。全批 3600 秒，不能超过批次 Token 上限。

## 用量与停止

每次调用前持久化预留 34,816 Token（模型最大输入 30,720 加本批最大输出 4096，保守高估）。只有完整非负整数用量回执才按实际输入与输出结算；未知用量保留整笔预留并停止整批。剩余额度不足下一次完整预留时停止，不以字符数估算代替硬限。框架调用与工具循环使用同一连接包装器。

遇到账号/免费额度错误、未知用量、取消、代码/数据/资格证据漂移、容器清理无法确认或批次资源上限，停止整批并保留未运行行。网络超时不自动重发。

本地账本控制本批调用 Token；“免费用完即停”由用户确认的服务端开关执行。真实账单没有在本地 API 回执中返回，不能把原价估算写成实际支付金额。

## 验收和指标

所有候选从原始基线独立重建，文件白名单、原测试不变；首次通过可见测试的候选只做一次独立验收，不将独立测试反馈交给模型重试。

逐次保留模型可见消息、工具 schema、输出、用量、候选 diff、原测试/独立测试报告及停止原因。汇总维度：独立验收通过、可见测试通过、首个候选通过、请求数、实际输入/输出 Token、单任务耗时、执行工具数、源码读取和重复读取、候选拒绝/错误。用量缺失显示未知。

在同题同重复配对上比较，两组共同通过的任务另外列出成本；不能用失败后提前停止带来的低用量称“节省”。不以两题小样本推断全项目成功率，也不将 Agent 响应耗时等同于被修复程序的运行速度。
