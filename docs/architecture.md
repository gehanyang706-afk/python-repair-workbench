# 架构与验证规则

## 交付版业务调用链

网页或命令行提交仓库、Git 修订、任务描述与批准文件 → `api.py` / `__main__.py` 校验输入 → `service.py` 将网页任务写入 `storage.py` 的 SQLite 队列并固定提交 SHA → `snapshot.py` 从 Git 对象创建不可变基线 → `runner.py` 在 Docker 中复现原始测试 → `agent.py` 按默认 `v2` 配置调用 Deep Agents → `session.py` 管理权限、预算、候选与事件 → `edits.py` 检查局部替换的版本、位置与唯一性并做语法预检 → `candidate.py` 构建候选及补丁 → `verification.py` 用同一镜像在独立副本中运行原始测试 → `service.py` 持久化结果，网页展示前后测试、日志和补丁并提供下载。原仓库不被修改。

`--profile full` 显式启用 `source_context.py` 与 `repair_contract.py` 的 v3 导航及需求审查；它不改变 Session、Docker 或 Verification 的权限边界。真实 Bug 评测由 `evaluation.py` 独立编排，额外使用模型不可见的验收测试评分，不属于普通网页任务的完成判定。网页任务的“验证通过”只表示原始测试范围通过。

本机服务只监听 `127.0.0.1`，单执行器串行处理任务。`storage.py` 保留完成结果、事件和重启后的中断状态；不会自动重放中断的模型调用。详细运行和边界见 [本机工作台](web-workbench.md)、[Agent 运行](agent-runtime.md)及[本机部署](deployment.md)。

## 数据流与模块边界

调用方 → `__main__.py` 参数解析 → `snapshot.py` 从 Git 对象导出基线 → `runner.py` 执行容器测试并记录失败 → `candidate.py` 校验批准范围、建立候选、导出补丁 → `verification.py` 从原基线重新构建验证副本 → 同一镜像 ID 内运行原始测试 → 输出结论。

模型只提供候选源代码与诊断。修改批准范围、测试执行命令和修复判定属于应用控制，不交给模型自行决定。

快照从指定提交导出，不复制工作目录中的未提交修改；拒绝符号链接、子模块，限制 2000 个文件和总计 20 MiB。运行前校验文件哈希，执行记录绑定内容标识。基线、候选、验证目录彼此独立且不能覆盖旧记录。

候选只允许修改明确批准的现有 Python 源文件，不能修改测试与配置。验证模块从实际哈希差异重新推导改动，不信任候选自报的修改列表；在原基线副本上重新应用源文件内容。因此，候选的测试文件不会直接用于最终执行。

## 修复判定

1. 原基线必须真实复现测试断言失败，不能以依赖缺失或收集错误作为目标故障。
2. 前后镜像 ID 一致，容器清理已确认。
3. 前后测试身份集合一致，不能删除测试换取成功。
4. 原通过项继续通过，原失败项全部通过，不能以跳过替代修复。
5. 候选测试整体通过，才给出 `passed_original_test_scope`。

测试回归、故障未修复、测试集合变化属于修复否决；环境异常、超时、报告不可用、清理未确认属于无法确定。通过仅覆盖当前原始测试范围，不证明所有输入下的业务语义正确。

## 执行边界

Docker 无网络、只读根文件系统和代码挂载，限制 CPU、内存、进程数，移除 capabilities，限制临时目录大小。执行固定 pytest 命令，不接受模型生成的 Shell 命令。日志和 JUnit 报告写入本次独立报告目录。

当前仅适用于自有受控仓库：JUnit 报告仍由测试进程生成，源代码也可能影响测试行为，不构成恶意代码防作弊系统。哈希用于内容一致性检查，不是签名或访问控制。应用必须控制批准清单、基线和报告目录的写入权限。

尚未具备：日志磁盘配额、可靠崩溃恢复、多用户隔离、完整密钥扫描、独立镜像供应链及任意项目依赖适配。文件权限未纳入内容标识；只读挂载也可能不适合需要在项目目录写文件的测试。部分异常可能留下未完成目录，应保留排查并使用新输出目录重试。
