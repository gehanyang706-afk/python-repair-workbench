# 统一工具调度与可复核诊断证据

本轮将MCP用于两个具体业务职责：运行隔离诊断，以及独立查询已有测量证据。主Agent根据证据选择工具，独立验收器继续控制最终结论。原缺陷修复与SWE-bench入口没有自动启用这些性能诊断能力。

## 业务闭环

```text
主Agent提出假设
  → ToolRuntime调度本地AST/源码工具或MCP诊断执行器
  → CPU/内存/耗时诊断在Docker运行，结果绑定源码版本并落盘
  → 模型先接收有界摘要，必要时按引用分页查询MCP证据服务
  → 可选择少量真实证据引用，交给隔离的只读Investigator调查
  → 主Agent提交受控补丁
  → 独立重建并复验功能、性能、内存与回归约束
```

执行服务只有`list_diagnostics`、`run_probe`、`read_report`，保持一任务一次执行的边界。新增证据服务只有`list_reports`、`query_report`，并发布`diagnostic://catalog`及每份报告的摘要Resource；没有Docker执行、编辑、任意文件读取或模型调用能力。两个服务职责不同，复核者无需启动原Agent或重新运行测量。

## 工具调度

- 同一诊断任务共享一个ToolRuntime，本地业务工具、框架读文件/待办工具，以及`mcp:diagnostics`、`mcp:reports`使用同一调度器。默认物理调度速率40次/秒，任务内同时调度上限4、单端点上限2；工具权限和主子预算仍由应用检查。
- 缓存键包含端点、操作、参数及不可变证据包版本。只有经过校验的纯报告查询启用缓存与相同并发请求合并。失败不缓存，不自动重试。每个逻辑查询先扣应用工具额度，命中缓存仍不能绕过预算和取消检查。
- 运行探针沿用原有“源码快照+工作负载+探针种类”去重；新候选版本重新测量。源码读取会生成引用，假设更新、补丁提交及独立验收有状态，均不缓存返回值。
- 事件区分本地执行、远端连接、远端执行、协议校验、超时，以及结构化状态标识的鉴权、额度和限流错误。不根据错误文案猜测，不把异常全文写入调度日志。保留原始预算停止和取消异常。
- 调度统计区分逻辑请求、实际调度、缓存命中、并发合并与失败；不将这些计数直接叫作“无效探索率”。

这是**同一任务、同一进程的业务操作调度限流**，不是多Worker或多机器的全局限流，也不逐条约束发现、校验等底层MCP消息。当前Agent图仍串行调度；并发合并与端点并发约束由并发契约测试验证，不宣称已运行并行多Agent生产负载。MCP使用本地stdio；没有远程HTTP/OAuth接入或长连接池。独立证据服务可持续处理客户端请求，应用侧首次查询按需启动服务，重复同页查询由任务缓存复用。

## 上下文边界

CPU观测在完整证据文件中保留每个规模最多15条热点，模型默认视图每个规模仅返回前3条，并提供`read_probe_report`导航。报告分页可选择summary、hotspots、samples或environment；每页1—10条，响应上限16 KiB。源码版本、证据引用与报告身份随页面返回，测量样本不能脱离来源。

可选Investigator继续使用Deep Agents原生isolated模式和原生task工具。需要上游证据时，主Agent将description设为JSON字符串：

```json
{"question":"调查资源查找是否重复执行","evidence_refs":["E0002","E0003"]}
```

应用只解析最多4个已发放引用，生成最多6000字符的结构化观察。源码片段、父消息历史、长日志和补丁答案不进入上游包；CPU摘要最多3条热点。子Agent仍可在原有只读权限内按需调查，返回带引用的短结论。伪造引用在子Agent启动前拒绝；兼容原有普通问题字符串。主子请求、工具、截止时间与主流程预留继续共享。

## 独立复核报告

执行服务的配置由应用生成；证据服务读取操作方明确导出的冻结证据包。导出校验原证据摘要、完整报告哈希、源码版本、镜像、工作负载、探针实现以及实际样本；只导出测量与来源字段，排除主机路径、执行命令、原日志、源码与密钥。证据包在服务启动时按指定哈希读取并固定到内存。

已有诊断任务可导出证据，两个命令均不调用模型：

```bash
.venv/bin/python -m repair_workbench.diagnostic_reports --run runtime/example/agent --output runtime/example-evidence.json
.venv/bin/python -m repair_workbench.diagnostic_report_mcp --bundle /absolute/path/example-evidence.json --sha256 <上一步输出的sha256>
```

其他MCP Host可用第二条命令作为stdio服务启动配置；已通过官方SDK独立Client验证，没有声称已连接某款桌面客户端。新记录使用完整报告哈希绑定；旧归档若缺少该字段会拒绝导出，不能事后回写历史证据伪装绑定。

## 验证口径

最终完整回归471项：455通过、16项MySQL集成检查未启用而跳过、0失败；Docker与MCP已启用。测试覆盖真实stdio工具调用、Resource发现与读取、两类MCP服务贯穿实际Agent链路、独立Docker复验、缓存额度扣除、并发合并、跨端点速率约束、取消、错误归因、越界参数、篡改与上下文隔离。安装包49项产品文件一致性通过；从独立安装目录启动的报告服务与冻结页面一致。

完整链路的两次相同页面查询中，一次实际调度、一次缓存命中；该串行轨迹的并发合并数为0。该案例原始CPU热点数量较少，完整证据JSON与默认视图均为2197字节，没有观测到视图裁剪收益；较长报告的裁剪机制另由契约测试验证。首次测量噪声和旧入口兼容失败日志均保留，不改变性能阈值。完整结果、源码指纹与证据清单见[机器可读交付记录](mcp-runtime-delivery-20261104.json)。

这些验证证明工程机制与真实通信链路可用。脚本策略和已知补丁不等于真实LLM自主诊断；未在本轮调用模型API，也没有修复率、Token或实际业务时延提升的结论。
