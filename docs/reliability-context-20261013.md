# 请求可靠性与轻量上下文：工程验收

日期：2026-10-13。`main` 开发版本为 `1.1.0.dev0`；`v1.0.0` 标签及历史评测不变。本轮没有调用真实模型。新上下文和审查能力均通过实验配置启用，服务默认仍为 `v2`。模型请求生命周期修复适用于内置 DashScope 客户端的全部配置。

## 已复现的根因与修复

### 混合工具结果

旧恢复逻辑只看最后一条 ToolMessage。同一响应包含两个参数错误的编辑调用和成功读取时，错误可能计为 0 或 1；调换顺序会改变结果。新增失败测试实际复现了漏计和错误循环多调用一次的问题。

`tool_recovery.py` 按当前工具轮次与工具调用 ID 收集全部业务工具结果。收据键为 `(round, call_id)`，忽略旧轮次、未知 ID 和重复结果；成功读取不会清除同轮失败。每个失败调用单独计数，多项错误一起反馈，只安排一次恢复。错误字段按固定 Schema 名称白名单记录，不保存被拒参数值；调用 ID 和 JSON 错误使用摘要标识。

错误指纹连续重复时停止；最多准入两轮恢复，正常、恢复和框架摘要调用共享原模型预算。预算已经耗尽时，已收到的错误仍计数，但恢复次数不增加。框架摘要调用保留未处理的工具轮次，不注入修复指令或覆盖其状态。混合有效调用与无法解析的调用也会在有效工具执行后统一反馈。

### 模型超时与取消

已安装 SDK 的 `dashscope/common/constants.py` 定义传输参数 `request_timeout`，默认 300 秒。离线构造 SDK 请求实测：传 `timeout=30` 时传输仍为 300 秒；传 `request_timeout=(5,30)` 时才进入正确的连接/读取配置。原 `settings.py` 用错参数，解释了为何曾观察到 75 秒响应。

内置客户端改为 `ManagedTongyi`，将一次 SDK 推理放入专用请求进程，仍使用既有 ChatTongyi、Deep Agents 和工具 Schema。它不是另一个 Agent。凭据仅通过私有 stdin 传输，不在命令行、文件或事件中保存；子进程和父进程均关闭第三方 tracing。请求进程正常退出时关闭 SDK 连接池；终止时操作系统释放本地套接字和进程资源。

| 控制 | 当前值与语义 |
| --- | --- |
| 连接超时 | 5 秒；网络连接阶段限制 |
| 读取超时 | 30 秒；requests 的读取等待限制，不能代替完整墙钟上限 |
| 单次调用墙钟上限 | 30 秒，包含请求进程启动和 SDK 导入；到期停止整个本地请求进程 |
| 任务截止与取消 | Session 的单调时钟/取消回调，在请求等待中约每 50ms 检查 |
| 回收 | SIGTERM 后等待 0.3 秒，必要时 SIGKILL 后再等待最多 1 秒；回收确认后才返回 |
| 重试 | LangChain 重试为 0；关闭固定 SDK 内部 ConnectionError 的额外重发 |

SDK 的连接重发开关不是公开配置，故在私有请求进程中适配固定版本的 `_send_with_retry`，并在 finally 恢复和关闭连接池。这项适配有离线契约测试；升级 SDK 时须复核它。

`model_call_timeout`、`deadline_exceeded`、`cancel_requested`、连接/读取超时和请求进程清理失败具有不同停止原因。CLI 中断也会回收请求并保存停止状态。若清理不能确认，不宣称取消成功；本机执行器停止消费后续任务并保留锁，操作方需检查事件中的 PID。取消过程中没有返回的供应商用量标记为不完整，不能推断费用为零。

已验证阻塞进程退出、抵抗 SIGTERM 后被 SIGKILL 回收、本地连接 EOF、任务取消、截止时间、CLI 中断，以及网页服务的任务取消穿透到在途请求。它证明本地请求不在后台继续运行；不能保证服务商停止已经接收的远端推理或退款。自定义注入的同步模型不具备内置受控客户端的强终止保证。

### 读取反馈

源文件和日志读取改用安全原因码与字段约束，不返回原始 OSError 或敏感文件路径。

| 原因码 | 字段 / 可修正信息 |
| --- | --- |
| `invalid_source_path` | `path`；规范快照相对路径，禁止绝对路径及穿越 |
| `path_not_in_baseline` | `path`；从 list_sources 选择 |
| `invalid_start_line` / `start_line_out_of_range` | `start_line`；最小 1、最大为实际文件行数 |
| `invalid_line_count` | `line_count`；1–200 |
| `source_too_large` / `source_not_utf8` | `path`；最多 1 MiB，UTF-8 |
| `source_unavailable` / `baseline_version_changed` | 读取不可用 / 快照一致性失效；不透露底层异常 |
| `invalid_log_attempt` / `invalid_log_offset` | 当前候选编号范围 / 非负偏移 |
| `test_log_unavailable` | 对应日志产物不可用 |

简化读取工具采用严格整数类型，布尔值和数字字符串不会悄悄变成行号；范围限制仍由应用根据实际文件检查。上述拒绝保留读取权限和工具预算边界。

## 独立实验开关

| 配置 | source_ref 编辑 | 失败驱动上下文及导航 | 行为摘要与 diff 风险提示 |
| --- | --- | --- | --- |
| `simple_edit` | 是 | 关闭 | 关闭 |
| `simple_context` | 是 | 开启 | 关闭 |
| `simple_review` | 是 | 关闭 | 开启 |
| `simple_full` | 是 | 开启 | 开启 |

`result.json` 的 `features` 明确记录开关；`strict_review` 与 `advisory_review` 不混用。旧 v3 `full` 保留原强制审查，仅用于既有实验；新 simple 配置不开放 `set_repair_plan`。

初始包只读取公开 JUnit 失败身份、日志头尾有界窗口、快照内堆栈位置、任务符号和公开失败测试的静态调用名称。断言没有业务源码堆栈时，通过公开测试中的调用名称定位批准源文件中的函数或构造方法；它是静态名称启发式，不是完整调用图解析。实际堆栈位置优先，按函数去重。最多三段原文、每段最多 2,000 字符，总 JSON 不超过 12,000 字符；所有引用绑定实际返回的原文。缺失可选日志时提供警告，不新设提交硬门槛。

字面搜索复用原工具：增强配置最多八个命中，附带所属符号、短原文与 source_ref，减少连续查目录和读文件头。符号读取继续使用 AST，完全不导入或运行目标代码。simple 配置的重复读取会重新交付内容及新引用，避免假定模型仍保留旧上下文；事件保留 `purpose`，区分初始上下文、搜索附带读取和普通工具读取。

`record_behavior_summary` 可记录需要改变、应保留和相关入口，无引用表单、哈希或计划 ID，且可省略。摘要标记为模型分析。`repair_contract.py` 根据真实候选与原基线 diff 生成实际函数范围、行区间及比较、分支、异常、签名、状态、多符号等风险。语义风险不阻断候选，也不是正确性证明；静态解析不完整时返回警告并保留 Docker 验证。

## 业务调用链

此前：任务入队 → 固定快照 → Docker 公开失败复现 → Agent 逐段读取 → source_ref 局部提交 → 权限/匹配/语法检查 → Docker 原测试验证 → 补丁审核。

现在：任务入队 → 固定快照 → Docker 公开失败复现 → 可选有界初始上下文 → Agent 经受控请求进程调用模型 → 按调用 ID 处理工具结果及有限恢复 → 具体读取反馈、可选符号/搜索和行为摘要 → source_ref 原子编辑 → 版本/权限/唯一匹配/去重/语法预检 → 可选实际 diff 风险报告 → Docker 重建原测试并验证 → 输出补丁、停止原因、风险和用量完整性 → 人工审核。

离线 Evaluation 在公开通过后额外验证同一候选的独立测试。生产任务没有隐藏答案，验证范围仍为原始测试。SQLite 队列、单 Agent、Docker 隔离和独立重建职责均未改变。

## 计数与历史可比性

候选预算及评分不变：进入提交方法的请求和预检拒绝占候选额度；Schema 拒绝不进入候选流程，但消耗共享模型预算。新修复补全了按 ID 的错误计数：混合轮次中的全部失败调用分别统计，恢复次数改为实际准入的恢复轮次，最多 2。不能直接与旧漏计数据比较错误率。

新增强制调用墙钟停止和正确网络超时会影响结果：过去 40–75 秒才返回的响应现在可能停止，且 SDK 不再重发连接错误。新评测记录包含连接、读取、墙钟上限、重发策略和进程隔离参数；必须重新运行同生命周期下的基础配置，不能将与历史成功率的变化全部归因于上下文或审查。

历史成对审计工具保留原默认两配置规则，并支持显式 `profiles` 矩阵。`--allow-code-change` 只允许当前实现漂移，仍核对历史各运行之间的代码、数据集、预算、模型配置、镜像、测试身份、候选和用量一致性。

## 离线验收与限制

真实任务资格核验：boltons `bits-empty-conversion` 和 more-itertools `bucket-falsey-validator` 均合格，模型调用 0。八个任务/配置组合的初始上下文检查通过；上下文关闭的配置初始包为 0，开启配置中前者为 3,726 字符、三段原文，后者为 1,906 字符、两段原文，包含批准源码入口且不含隐藏测试。旧版只找到公开测试片段的检查证据也保留，未覆盖。

历史两题付费记录继续通过审计；当前实现指纹漂移单独标记。所有八个固定任务的数据集文件保持原 SHA-256。本轮使用确定性模型及本地慢进程测试替身，真实服务调用 0；不产生新的 Agent 修复成绩。

最终完整回归：`RUN_DOCKER_TESTS=1 .venv/bin/python -m unittest discover -s tests -v`，148 项全部通过，44.840 秒；记录为 `runtime/light-context-20261013-verified-tests.log`。覆盖混合顺序、多失败、去重与恢复预算、阻塞响应/截止/取消、SIGKILL 与连接关闭、清理失败保锁、严格行号、读取边界、隐藏测试排除、独立开关、实际 diff 提示和原有网页/Docker 链路。

原始验收记录位于忽略 Git 的 `runtime/light-context-*20261013*`。使用本机已有构建工具离线构建 `1.1.0.dev0` wheel，检查请求模块及网页静态资源纳入安装包；未安装或下载新依赖。下一轮真实模型控制方案见[评测计划](light-context-evaluation-plan.md)。

仍有限制：静态名称匹配不能可靠解析别名或动态调用；大日志只取有界窗口，可能遗漏中间失败；AST 风险不能证明需求覆盖；请求进程控制实测主机为 macOS，Linux 主机未实测，Windows 不支持该 POSIX 进程组实现；真实供应商长响应、网络故障及新机制对修复结果的影响尚未验收。强 30 秒限制可能影响此前长响应任务，需在新对照中作为共同条件观察。
