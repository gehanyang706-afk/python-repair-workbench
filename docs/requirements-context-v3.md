# 需求约束与源码上下文优化 v3

本文件记录 v3 实现和原始评测方案。`full` 的付费评测已完成，结果见 [v3 评测](evaluation-v3-20261012.md)；1.0.0 的默认产品流程为 `v2`，额外消融实验暂未启动。

## 业务变化

旧流程：固定 Git 提交 → Docker 复现公开失败 → Agent 按行读取源码与日志 → 局部提交或整文件兼容提交 → 版本/位置/权限/语法检查 → Docker 原测试验证 → 评测器独立验收。

v3 `full` 实验链路：固定提交 → Docker 复现 → Agent 获得批准文件的有界符号目录及失败日志摘录 → 按范围读取或检索可见源码 → 登记任务要求、保留约束和预计修改符号 → 局部或完整提交 → 原有版本/权限/重复/语法检查 → 需求覆盖声明、源码符号范围和风险审查 → Docker 原测试验证 → 公开通过后由评测器执行独立验收。所有候选仍从原始快照派生，不修改原仓库。

Session 负责工具预算、读取事件、候选次数与检查顺序；`source_context.py` 只静态解析可见 Python 源码；`repair_contract.py` 核验需求引用和修改范围；Agent 负责提出计划、补丁和解释。评测器仍在独立目录加载未展示给 Agent 的验收测试，评分与通过条件不变。

## 需求与约束检查

`set_repair_plan` 要求模型分别列出 `change` 和 `preserve` 项。每项必须引用任务描述中的原句，并给出可见快照文件的 SHA 与有效行范围。可修改符号必须属于应用预先批准的源文件，且在当前快照实际存在。此处只核对引用和版本，不能自动判断需求清单是否完整或模型解释是否真实。

提交时 `assessment` 按计划 ID 覆盖全部条目。静态审查从原文与候选源码比较函数、方法、模块顶层及类状态；修改超出声明符号时拒绝。签名、比较条件、异常、定义增删、模块/类状态和纯文本修改需要模型关联至少一个保留约束并说明理由。审查只提示明显风险，不宣称证明语义正确；错误声明仍可能通过，最终依赖公开与独立测试。原有权限边界仍禁止修改测试、配置、未批准文件。

一次进入 Session 的提交仍占一个候选名额。审查拒绝后，允许同样源码配合修正的计划/风险说明重交，因为该候选尚未执行；语法错误和已验证内容仍按原规则去重。这个差异使 v3 与 v2 的候选类型统计不完全一致，报告必须分别列示预检、审查和 Docker 阶段。每题模型调用/候选/时间上限未提高。

## 读取观测和上下文获取

旧 v2 运行日志只存业务工具名称。根据事件重新统计，原四题共 26 次 `read_source`；其中空名称题 11 次读取、12 次模型调用、零候选。旧日志没有范围或返回内容，无法计算历史重复率与有效信息比例。框架 `read_file` 只可从模型请求名称部分观察，不计入 Session 的业务工具调用数。

`observe` 配置保持 Agent 原工具与用户消息内容，额外记录每次源码读取的路径、版本、起点、请求/返回行数、新增行数、重复标记、返回字符数和内容摘要；不记录源文本或模型的原始工具参数。`context` 增加批准文件符号目录、受限字面搜索、按符号原文读取，并对完全相同的读取请求返回上次内容摘要和定位建议；`force=True` 可重新获取。搜索最多 30 项，单次读取最多 200 行、16K 字符，均从不可变快照获取。初始上下文仅含最多 8 个批准文件的结构与最多 2500 字节公开基线日志，内容序列化后不超过 12K 字符。目录最多 100 个符号，较大文件可改用搜索和分段读取。

日志能量化读了多少、重复了多少以及模型调用/token；无法从这些代理指标直接判定哪些上下文对修复有用。重复抑制可能在模型丢失早期上下文时反而不利，因此保留 `force`，并须通过真实模型对照验证效果。

## 对照配置

- `v2`：旧业务行为兼容配置；运行在新代码上，不等于历史 v2 代码指纹。
- `observe`：只加读取记录，适合作为本版本对照。
- `context`：读取记录及定向检索、重复读取提示。
- `review`：读取记录及需求/范围审查，不启用新检索工具。
- `full`：同时启用检索与审查，供显式实验使用；正式 `repair` / `serve` 已改为默认 `v2`。

评测命令显式 `--profile` 并在结果中记录配置；缺省为 `observe`，避免误把全功能实验当旧基线。所有配置使用同一 Session 权限、Docker 镜像、模型配置、调用及候选预算、测试身份和独立评分。`observe` 的工具签名已因统一入口增加可选参数，因此也不能声明与旧 v2 的模型输入逐字相同。历史 0/4、v2 1/4 与 2/2 的目录和指纹保持原样；后续因果对照必须在本版本相同代码下切换配置，新目录不可覆盖旧结果。

## 跨项目任务

`benchmarks/cross-project-v1/` 包含 more-itertools 两个固定上游历史修复：布尔值为假的有效 validator 仍应生效；`constrained_batches(max_count<=0)` 应拒绝。文件、上游父提交与修复提交、许可证和测试全部哈希绑定。公开测试及评测器独立测试分别核对原版失败、官方修复通过，共 8 次 Docker 运行，2/2 任务资格合格。资格合格不代表 Agent 成功；这是继 boltons 后第二个上游项目，仍是精选模块级案例，不代表广泛泛化能力。

## 验证与限制

自动化覆盖读取统计与重复抑制、合法/非法目录及搜索、证据版本/范围、任务引用、批准符号、越界修改、比较/签名/异常风险、审查拒绝后重试、模型工具配置及真实 Docker 全链路。测试模型为确定性脚本，不是 qwen-plus；本阶段模型调用为零。完整运行结果见 `runtime/v3-all-tests.log` 和跨项目资格报告 `runtime/cross-project-v1-qualification-20261011/`。

当前对重复定义同名符号采取保守拒绝；审查配置中新增函数由于无法在原快照预先批准符号，也会被拒绝；此类任务会保守拒绝。静态审查不是需求证明，用户仍应审阅补丁。大型文件的初始目录可能截断，模型需要搜索定位。没有付费评测时，不能声称真实成功率或 token 使用已经改善。

## 原付费评测方案（归档）

先在原四题上运行 `full`，在跨项目两题上单独运行 `full`；保持 qwen-plus、每题最多 12 次模型调用/3 候选、原有超时和独立评分。六题总上限 72 次模型调用，不自动扩容。旧结果按原四题与新跨项目组分别报告；没有用旧模型在跨项目题上的对照，不能宣称那里有提升。

要拆分机制贡献，再对原四题分别运行 `observe`、`context`、`review` 与 `full`，同版同题同预算比较。四配置各四题最多 192 次调用；如果先完成 `full`，其余三配置增量最多 144 次。实际执行前需再获得单独的批量付费许可，并检查模型地区和账单价格。按 2026-10-11 [阿里云 qwen-plus 官方价格](https://help.aliyun.com/zh/model-studio/qwen-plus)中北京地区非思考、每次输入不超过 128K 的 ¥0.8/百万输入 token、¥2/百万输出 token，六题主实验的 4–12 调用/题、每次 8K–32K 输入与 1K–4096 输出场景约 ¥0.20–¥2.43；四配置原四题再加跨项目两题的完整对照场景约 ¥0.60–¥7.30。均为场景估算，不是费用硬上限或实际账单。
